 为什么随机数据压不动

    

      
      
        N 个字节有 28N 种可能。任何无损压缩都把它们映射到更少的压缩串上——
        可压缩串的数量小于原始串，必然有至少两个原始串对应同一个压缩串，解压时无法区分。
        所以「真正随机的数据不可压缩」不是实现不行，是数学上不可能。
        刚才 LZW 压噪声不但没变小，反而因为要附带字典而变大——这就是证据。
      
    

  


  
  

    
 核心代码

    

      
# 编码：边读边学
字典 = 输入里每个不重复字符（按首次出现顺序）→ 编号 0,1,2...
词 w = 空
for 字符 c in 输入:
    if w + c 在字典里:      # 认得，先攒着，还能更长
        w = w + c
    else:                   # 不认得了：把 w 报出去，把 w+c 学进字典
        输出 字典[w]
        字典[w + c] = 下一个编号
        w = c
输出 字典[w]                # 收尾，最后一个词也要报

# 解码：不碰原文件，重建出同一个字典
for 编号 k in 编号流:
    输出 字典[k]
    字典[下一个编号] = 上一个词 + 本词首字符   # 和编码器同步学习

    

    

      真正的 LZW 还要处理「编号 9 位变 10 位、10 位变 11 位」的变长打包和清字典位；
      这里为了可读性用定长编号。核心思想一行没省：能匹配就攒，攒不住就报编号、学新词。
    

  


  
  

    
 原理：三张卡看懂 LZW

    

      

        
01

        
先来后到

        
字典从空开始，边读边建：第一次见到的字符先拿小号编号，后来发现的重复短语按顺序排队拿大号。谁先出现，谁先有名字——编号小的词条一定比编号大的更早出现。

      

      

        
02

        
命中缓存

        
重复片段只记一次编号，下次整段直接说「就那个」。第一次读「所谓伊人」要花 4 个编号，第二次读到直接报一个编号——字典越长，单次省得越多。

      

      

        
03

        
无损的保证

        
解码器不依赖原文件：只要拿到「字母表 + 编号流」，就能重建出与编码器一模一样的字典。编号一一对应，所以压缩再狠，解压出来也一字不差——这是数学保证，不是工程尽力。

      

    

    

      
 姊妹篇：有损 vs 无损

      
本站的 JPEG2000 演示讲「有损压缩怎么丢数据」——把人不敏感的高频细节扔掉换体积；这里讲「无损压缩怎么一个字都不丢」——把重复记住、把冗余删掉。有损靠人眼，无损靠字典，两篇合起来就是一套压缩专题。

    

  


  
  

    
 一篇 1977 年的论文，活到今天

    

      

        

        
GIF（1987，老而不死）

        
CompuServe 发布时选 LZW 当心脏，一张动图能压到原来的几分之一。1990 年代因专利打了一场大官司，但 GIF 至今还是表情包的原生格式。

      

      

        

        
PNG

        
PNG 内置的 DEFLATE 压缩 = LZ77（LZ 家族第二代）+ 霍夫曼编码。GIF 之后，无损压缩扛把子的位置传给了 LZ 家族。

      

      

        

        
Unix compress

        
1984 年 Spencer Thomas 把 LZW 写进 Unix，一条 compress 命令压缩率吊打当时的霍夫曼压缩器，从 BSD 一路活到 Linux 的默认工具箱里。

      

      

        

        
TIFF

        
扫描仪和印刷界的 TIFF 标准把 LZW 列为内置压缩选项，二十多年没变过。文档格式的宿命就是：标准定了，算法就永生。
