🧮 收费站是怎么算钱的
C++ 赢的条件： b + N·v < N·j

j 是 Java（JIT 编译后）每次操作的耗时，v 是 C++ 纯计算耗时，b 是过一次境的固定过路费， N 是攒多少次操作再过境。整理一下，交叉点在 N* = b / (j − v)： C++ 的速度优势每小时能挣 (j − v) 纳秒，先把过路费 b 挣回来，剩下的才是纯赚。 批量拉到无穷大，加速比的天花板是 j / v——过路费摊到零也到不了更高的地方。

对应到真实 JVM：ArrayList.get 这种纳秒级操作，JIT 把它内联成几条机器指令， 而一次 JNI 调用要切换栈帧、保存寄存器、挂异常检查点，量级在几十到几百纳秒。 每步都过境，等于把 5ns 的活干成 80ns——这就是单次过境反而慢十几倍的原因。 JVM 自己要下探到 C 层时走的也不是 JNI，而是 intrinsic：JIT 认出 System.arraycopy 这类方法，直接换上手写的向量化机器码，收费站都不过。

那什么时候过境划算？粗粒度的活：zlib 压一大块 buffer、读写一个 socket。 过路费只交一次，里面包着几千纳秒的正经活，曲线从第一格就压在 Java 之下。 java.util.zip 和 NIO 的 selector 就是这么干的。语言层面的后续也在印证这个模型： Valhalla 在给 Java 补值类型（把 j 本身做小），Panama 的 FFM API 在把过路费 b 降下来（比传统 JNI 便宜数倍，JDK 22 起正式可用）——两条路，都没打算把收费站修成高速路。

关于数字的诚实说明：本页的耗时是模型参数，不是某台机器的实测值。 量级参考公开的 JNI 开销讨论与 JMH 基准常识，公式全部摊开可复算——拖动旋钮，曲线会告诉你结论对参数有多敏感。
